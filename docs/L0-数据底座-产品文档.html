L0 数据底座 — Content Data Platform

把全世界 AI Coding 相关内容采集进来，并尽可能完整、不可变地保存全部信息，成为整个平台唯一可信的数据真相源，为上层（L1–L3）提供数据驱动。这一层的信条只有一句：数据是最重要的资产，宁可多存，绝不丢失。

层级：L0（最底层） 形态：内部数据产品 / 平台服务 客户：L1 / L2 / L3（上层） 信条：全量保存 · 可追溯 · 可重放

1是什么

L0 是一个独立的数据产品：负责"把原始内容搬进来并完整保存好"，不做任何业务判断（评分、推荐都不在这层）。它对上层只承诺一件事——提供干净、统一、完整、可追溯、可重放的内容数据。

📥

采集一切

RSS、网页全文、播客、X/Twitter，多源接入，统一进库。

🗄️

完整保存

原文 HTML、抓取元数据、媒体、源头原始条目——全部留存，不裁剪。

🔁

可重放驱动

上层算法/模型升级时，可从原始数据重新加工，无需再抓一遍。

2为何它最重要

数据是平台唯一不可再生的资产。模型会换、评分标准会改、产品会迭代——但若当初没把原始数据存全，历史就永远丢了，无法补回。所以 L0 的设计原则不是"够用就好"，而是"尽可能保存所有信息"，把判断与裁剪全部推迟到上层。
  • 重放价值：L1 的摘要 prompt、L2 的评分 rubric 一旦升级，可对全部历史原文重跑，立刻获得"全量升级"的效果——前提是原文还在。
  • 信任价值：每条内容都能追溯到"哪个源、何时抓、原文长啥样"，让上层与用户都能信任数据。
  • 资产价值：随时间累积的完整内容库，是后续做搜索、训练、跨垂直综合的底层燃料。

3它的客户：上层

L0 是平台型产品，它的"用户"不是终端读者，而是上面三层。

客户它从 L0 要什么
L1 数据加工干净正文 + 元数据，用于基础分析；能按状态拉取待处理内容
L2 判断/Agent偶尔回溯原文做深度判断；源信息用于来源偏好
L3 产品/站点原文链接、来源、发布时间等展示用元数据
未来：外部/重放重新加工历史数据；潜在的对外数据服务

4全量保存原则（核心）

保存什么（尽可能全）

  • 源头原始条目（RSS entry / API 原始 JSON 全字段）
  • 原始 HTML 全文（未清洗）+ 抓取快照
  • 清洗后正文 + 抽取的结构（标题/作者/正文/图表）
  • 抓取元数据：URL、HTTP 头、状态码、抓取时间、耗时、渲染方式
  • 媒体资源：封面图、音频（播客）、关键图片
  • 多版本：同一 URL 内容更新时保留历史版本
  • 血缘/来源：哪个源、哪次抓取任务产生

保存怎么做（原则）

  • Raw-first 不可变：原始层只追加不修改，永不丢失
  • 原始与规范化分离：raw 存全、normalized 供查询
  • 去重但保留变体：同内容多源/多版本都留痕
  • Schema-on-read：未知字段进 jsonb，先存下来再说
  • 幂等：重复抓取不产生脏数据
  • 冷热分层：热数据在库，冷原文进对象存储控成本
取舍："尽可能保存所有信息"会带来存储成本。应对：原文等大块进对象存储（便宜），库里只留元数据与指针；冷数据转冷存储；但默认不删原始数据——存储很便宜，丢失的历史无价。

6对上层的数据契约

  • 查询接口：按状态/源/时间拉取内容；按 id 取完整内容（含原文指针）。
  • 事件：新内容入库时发 content.ingested，上层据此触发加工。
  • 稳定字段：id、canonical_url、title、clean_text、lang、source、published_at、status —— 对上层稳定不变。
  • 状态：L0 负责把内容推进到 WAIT_FILTER（已入库待加工），后续状态由上层推进。
契约即解耦：上层只依赖这份稳定契约，不关心 L0 内部如何抓取与存储。L0 可以随时优化采集实现而不影响上层——这正是"每层独立产品"的意义。

8独立性

L0 可独立部署、独立演进、独立验证：不依赖上层即可运行（只采集与保存）。理论上它本身就是一个可复用的"内容数据平台"，未来可服务多个垂直站，甚至作为对外数据服务。但它的价值只有在被上层消费时才兑现——它存在的全部意义是为上层提供数据驱动。

9边界：L0 不做什么

  • 不做业务判断：不评分、不打"好坏"标签、不推荐——那是 L2。
  • 不做内容理解：不摘要、不抽实体——那是 L1。
  • 不感知垂直：L0 不知道"AI Coding"，只知道"内容与源"。垂直归属是上层的事。
  • 不直接面向终端用户：不渲染页面、不管账户。
