L0 数据底座 — 架构设计

本文聚焦"如何把数据尽可能完整地采进来、不可变地存下去、并能驱动上层重放"。核心设计是三段式存储（原始层 / 规范层 / 索引层）与可重放的血缘体系。

1设计目标

🗃️

零丢失

原始数据不可变、只追加，永不覆盖删除。

♻️

可重放

上层升级可从原始层重跑，无需重抓外部源。

🧬

可追溯

每条规范化数据都能溯源到原始抓取。

🧩

可扩展字段

未知/新字段用 jsonb 先存，schema-on-read。

💰

成本可控

大块原文进对象存储，库存指针与元数据。

🔌

稳定契约

对上层暴露稳定字段与事件，内部实现可换。

3三段式存储模型（核心）

① 原始层 RAW

不可变、只追加。保存源头原始条目、原始 HTML、HTTP 头、抓取快照、媒体二进制。大块进对象存储，库里存指针+校验和。这是可重放与零丢失的根基。

② 规范层 CANONICAL

从原始层派生的统一 ContentItem：清洗正文、标题、作者、语言、发布时间、状态。上层主要消费这层，可被重放重建。

③ 索引层 INDEX

去重指纹、源健康、抓取日志等运维/查询辅助。可重建，不含真相。

为什么分三段：原始层保证"存全不丢"，规范层保证"上层好用"，索引层保证"查得快、管得住"。派生层(②③)永远能从原始层(①)重建，所以即便规范化逻辑出错，原始数据仍在，可重跑修复。

4数据模型（深化）

-- ① 原始层（不可变，只追加）
raw_documents(
  id, source_id, fetch_job_id,
  url, http_status, http_headers jsonb, fetched_at, fetch_method [rss|browser|api],
  raw_entry jsonb,            -- 源头原始条目(RSS/API 全字段)
  raw_html_ref,               -- 对象存储指针(完整原文)
  raw_html_sha256,            -- 校验和(完整性/去重)
  media_refs jsonb,           -- 封面/音频/图片 对象存储指针[]
  extra jsonb )               -- 任何额外/未知字段，先存下来

-- ② 规范层（派生，可重建，上层主消费）
content_items(
  id, canonical_url, url_hash UNIQUE, content_hash, simhash,
  title, author, clean_text_ref, lang,
  source_id, published_at, fetched_at,
  current_version int, raw_document_id → 溯源到原始层,
  status [WAIT_FILTER|...|COMPLETED|CANCELLED],
  meta jsonb )                -- 规范化的扩展字段

content_versions(           -- 同 URL 内容更新的历史版本
  id, content_id, version int, raw_document_id, clean_text_ref,
  diff_summary, detected_at )

-- ③ 索引/运维层（可重建）
sources(id, name, feed_url, type, crawl_config jsonb, is_public,
        owner_user_id?, vertical_codes[], etiquette jsonb)
source_health(source_id, last_ok_at, fail_count, empty_streak, status)
crawl_jobs(id, source_id, started_at, finished_at, stats jsonb, status)
dedup_index(url_hash, content_hash, simhash_bucket, content_id)
关键点：content_items 通过 raw_document_id 永远指回原始层；大文本/二进制只存对象存储指针 + sha256，库表保持轻量可查。extra/meta jsonb 接住一切未预料字段——先存，后定义。

5去重策略（去重但保留变体）

层级指纹处理
同一 URLurl_hash规范层合并为同一 content_item；内容若变 → 新 version
完全相同正文content_hash (sha256)判定完全重复；但原始抓取仍各自留痕(多源转载)
近似内容simhash近重复聚类；保留代表 + 关联变体，不丢弃
原则：去重是为"上层不重复处理与展示"，不是为了删数据。原始层永远保留每一次抓取（含转载变体），去重只发生在规范层的"代表选择"上。

6可重放与血缘

  • 血缘 (lineage)：content_item → raw_document → crawl_job → source 全链路可溯源。
  • 重放 (replay)：当 L1 摘要逻辑 / L2 评分 rubric 升级，触发"重处理"——从原始层读 raw_html，重建规范层与上层产物，无需重新抓外部源。
  • 重放接口：POST 重处理(范围: 源/时间/全部, 目标层: L1/L2) → 发 content.reprocess 事件给上层。
这是 L0 最高价值的能力：原始数据存全 + 可重放 = 上层算法每次升级都能"免费"作用于全部历史内容。没有完整原始层，这一切不可能。

7版本与变更检测

技术博客/文档常被更新。L0 用 content_hash 检测变更：内容变化时新增 version 行并更新 current_version，旧版本与其原始 HTML 全部保留。

8对上层的接口契约

# 查询（供 L1 拉取待加工）
GET  internal/contents?status=WAIT_FILTER&since=&limit=
GET  internal/contents/{id}        # 含 raw 指针、溯源

# 事件（驱动上层）
EVENT content.ingested {content_id, source_id, lang}
EVENT content.reprocess {content_id, target_layer}

# 稳定字段（对上层不变）
id · canonical_url · title · clean_text · lang · source · published_at · status

9采集时序

Scheduler 按源 crawl_config 触发抓取任务（遵守 robots / 速率 / 礼貌间隔）
RSS Poller 取条目 / Web Fetcher 用 Playwright 渲染抓全文 → 原样写入 raw_documents + 对象存储
Extractor 提取正文与元数据 → 计算 url_hash/content_hash/simhash
Dedup：新内容建 content_item；已存在则比对 hash，变更则加 version
写规范层(status=WAIT_FILTER) + 索引层；更新 source_health
发 content.ingested 事件 → 驱动 L1

11部署

MVP：ingestion-worker 进程 + Playwright（同镜像或独立）+ PG + Redis + 对象存储。规模化：抓取 worker 水平扩展，按源分片；任务锁避免重复抓取。

12重点考量（你要求"多考虑点"）

议题设计取向
存全 vs 成本默认全存；大块进对象存储；冷数据转冷存储；不删原始
原始 vs 规范分离原始不可变、只追加；规范可重建。两者强血缘绑定
幂等抓取按 (source,url,content_hash) 幂等；重复不产生脏数据
抓取礼貌遵守 robots、限速、退避、UA 标识；源级并发上限
失败可恢复抓取失败留 raw 记录与错误；可重试；不阻塞其他源
合规/版权规范层只供上层生成"摘要+链接"，不对外全文转载；标注来源
Schema 演进jsonb 兜底未知字段；新字段先存后建模，避免丢信息
数据质量正文提取置信度打分；低质量进人工/重抓队列（仍保留原始）
