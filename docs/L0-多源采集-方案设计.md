# L0 多源采集扩展 · 方案设计

> 目标：把 L0 从"只吃 RSS"扩成**可插拔的多源采集平台**，支持新闻、微博热搜、抖音热点、
> GitHub Trending、小红书等多种"文章型 / 榜单型"来源，并具备定时调度与配套界面。
> 本文档为**方案设计**（不含实现），确认后再编码。

---

## 1. 目标与范围

| 编号 | 需求 | 设计应答 |
|---|---|---|
| ① | 来源不限于 RSS，支持任意网站 | 适配器（Adapter）模式，按 `source.type` 分发 |
| ② | 可新建不同"爬虫任务"：微博/抖音/GitHub/新闻热点等 | 内置多类适配器 + 标准接口；加新站=加适配器，不动核心 |
| ③ | 定时功能 | 常驻调度循环 + 每源独立间隔 + Arq cron 生产方案 |
| ④ | 界面体现 | 新增来源支持选类型/间隔/参数；列表展示类型/下次运行；调度状态指示 |

**非目标**：本期不破坏 L0 既有契约（append-only 原始层、L0 自有表、禁止上层导入），不做 L1+ 的内容筛选/排序。

---

## 2. 关键设计洞察：两类来源

| 类别 | 例子 | 特征 | 入库路径 |
|---|---|---|---|
| **文章型** | RSS、普通新闻站列表页 | 每条目有独立正文 URL，需抓正文+抽取 | RSS/HTML→raw→**抓页+extract**→content_item |
| **榜单型** | 微博热搜、抖音热点、GitHub Trending、百度/知乎热榜 | 某时刻 N 条带"排名/热度"，多数无正文可抓 | 列表→raw→**直接落 content_item**（rank/heat 进 meta） |

因此适配器需声明 `needs_page_fetch`：文章型为 `True`（走现有抓页+抽取），榜单型为 `False`（轻量直接入库），这是本设计的核心分叉。

---

## 3. 架构总览

```
            ┌─────────────── crawl_source(source) ───────────────┐
            │  adapter = get_adapter(source.type)                 │
 source ──► │  for entry in adapter.fetch_entries(source):        │
 (.type,    │      raw_store.append(entry.raw)   ← append-only 不变 │
  .crawl_   │      if adapter.needs_page_fetch:                   │
  config)   │          fetch_page → extract → build_content_item  │  ──► content_items
            │      else:                                          │       (+ meta: rank/heat/platform)
            │          build_content_item_from_entry(entry)       │
            └─────────────────────────────────────────────────────┘
                              │ outbox: content.ingested
                              ▼  (relay 不变)
```

适配器只负责"产出条目"，落库/去重/outbox 全部复用现有逻辑——**契约面零改动**。

## 4. 适配器接口（草案）

新增 `core_data/ingest/adapters/`：

```python
# adapters/base.py
@dataclass
class Entry:
    url: str                       # 条目/帖子/仓库链接（榜单型可为话题页）
    title: str | None = None
    raw: dict[str, Any] = field(default_factory=dict)   # 原始 payload（落 raw_documents）
    published_at: datetime | None = None
    extra: dict[str, Any] = field(default_factory=dict) # rank/heat/platform/tags…

class SourceAdapter(Protocol):
    type: str
    needs_page_fetch: bool
    def fetch_entries(self, source: Source) -> Iterable[Entry]: ...

# adapters/__init__.py
_REGISTRY: dict[str, SourceAdapter] = {}
def register(adapter): _REGISTRY[adapter.type] = adapter
def get_adapter(type_: str) -> SourceAdapter: ...
def list_types() -> list[dict]:   # 供界面下拉 + 参数说明
    ...
```

`pipeline.crawl_source` 改为按 `source.type` 取适配器分发；保留 `kind="rss"` 之外也记录真实 type。

## 5. 内置适配器清单（按可行性分级）

| type | 来源 | 类别 | 可行性 | 说明 |
|---|---|---|---|---|
| `rss` | RSS/Atom | 文章型 | ✅ 开箱 | 迁移现有 `fetch_feed` |
| `html_list` | 任意列表/新闻站 | 文章型 | ✅ 开箱 | CSS 选择器从 crawl_config 取，覆盖大量普通站，无需逐站写码 |
| `github_trending` | github.com/trending | 榜单型 | ✅ 开箱 | 无需登录，HTML 解析，稳定；含 language/since 参数 |
| `baidu_hot` / `zhihu_hot` | 百度/知乎热榜 | 榜单型 | ✅ 较易 | 有相对开放的 JSON 端点 |
| `weibo_hot` | 微博热搜 | 榜单型 | ⚠️ 需配置 | 有 JSON 端点，可能需 cookie / 限频；做成可配 |
| `douyin_hot` | 抖音热点 | 榜单型 | ⚠️ 需签名 | 端点需签名，留扩展点 |
| `xiaohongshu` | 小红书 | 文章型 | ⛔ 扩展点 | 强反爬/登录墙，需 API 或 cookie，沙箱难验证 |

> ✅ 本期把 ✅ 级别做成可用并带本地 fixture 单测；⚠️/⛔ 留**标准接口 + 实现说明**，等你定 API/cookie 再填。
> 你提到的"新闻热点"主要由 `html_list` + 各站 RSS 覆盖；特定聚合源可后续加专属适配器。

## 6. 数据模型改动：尽量零改动

复用现有字段，**不加新表**（保持 L0 契约稳定）：

- `sources.type` —— 存适配器类型（rss / html_list / github_trending / …）
- `sources.crawl_config`(JSON) —— 存间隔与类型专属参数（见 §7）
- `content_items.meta`(JSON) —— 榜单型把 `rank/heat/platform/tags` 存这里
- `content_items.status` —— 榜单型可用新状态如 `TREND`（或沿用 WAIT_FILTER）

可选（非必须，若要按热度查询再加，需 Alembic 迁移）：`content_items` 增 `ix_content_items_source_status` 之类索引。
**本期倾向零迁移**，把榜单元数据塞 `meta`。

## 7. crawl_config 约定（各类型参数）

```jsonc
// 通用

// html_list
{ "list_url": "https://news.example.com/", "item_selector": "article a.title",
  "link_attr": "href", "title_selector": "", "base_url": "https://news.example.com" }

// github_trending

// weibo_hot
{ "top_n": 30, "cookie": "<可选>" }
```

界面新增来源时把这些作为"类型专属参数"（JSON 或动态表单）写入 `crawl_config`。

## 8. 定时调度方案（第③点）

现状：`scheduler.due_sources()` 已能按 `interval_min` 算"到点来源"，但**没有常驻进程在跑**（`worker.py` 仅骨架）。

设计两种运行方式：

1. **本地常驻脚本** `core_data.scripts.scheduler_run`
   - 循环：`due_sources()` → 逐源 `crawl_source` → relay outbox → sleep(tick)
   - 参数：`--tick-sec 60`、`--once`（跑一轮退出）、`--render`
   - 写心跳到 `source_health` / 一个轻量状态（供界面显示"调度器在跑/上次 tick"）

2. **生产 Arq cron**（接入现有 worker）
   ```python
   from arq import cron
   class WorkerSettings:
       cron_jobs = [cron(crawl_due, minute=set(range(0, 60, 5)))]  # 每5分钟
   ```

每源间隔仍由 `crawl_config.interval_min` 控制；`next_run_at = last_attempt_at + interval` 暴露给界面。

## 9. 界面改动（第④点）

**新增来源弹窗**：
- 「类型」下拉（来自 `GET /api/source-types`，含每类型参数说明）
- 「抓取间隔（分钟）」「是否渲染」
- 「类型专属参数」JSON 编辑框（或按类型动态字段）

**来源列表**：类型徽标 + 间隔 + 下次运行时间 + 健康度；行内"立即抓取/启停"保留。

**顶部/页脚**：调度器状态指示（运行中 / 上次 tick 时间 / 手动模式）。

**新内容呈现**：榜单型内容在「最近内容」里展示 `rank/heat`（来自 meta），状态徽标区分 `TREND`。

**后端接口新增/改**：
- `GET /api/source-types` —— 列出可用适配器及参数 schema（喂下拉）
- `POST /api/sources` —— 扩展接收 `type` + `crawl_config`
- `_status()` —— 来源项补 `type / interval / next_run`；调度状态字段

## 10. 契约与质量保证

- 原始层仍只经 `RawStore.append()` 写入 —— **append-only 契约不破**
- 适配器位于 `core_data.ingest.*`，**不导入上层**（满足 audit_dod 禁止导入检查）
- 全量 `ruff` + `mypy --strict` 通过；适配器用 `Protocol`/`dataclass` 强类型
- 网络代码与解析分离：解析函数吃 HTML/JSON 字符串，便于用**本地 fixture 单测**（沿用 tests/fixtures 模式），不依赖联网
- 扩展 `audit_dod` 认知适配器注册表（可选）

---

## 11. 法务与健壮性须知

- 遵守各站 robots.txt / ToS；内置**限频**与 User-Agent；失败留 raw 证据（已有机制）
- 平台型来源（微博/抖音/小红书）页面/接口变更会导致适配器失效——属预期，需维护
- 小红书/抖音绕过反爬有合规与封禁风险；**推荐走官方/授权数据源**
